# Long-Horizon Coding Agent：第一阶段执行方案

> 本文细化《Long-Horizon Coding Agent 项目执行方案（初稿）》的第一阶段任务。按可验证的工作节点推进，不按时间安排。本文是实施方案，不代表已经完成实现。

## 1. 第一阶段要完成什么

完成一个可运行、可演示、可评测的 Coding / Terminal Agent 基线项目。系统应能从任务说明和初始代码仓库出发，让模型多轮调用工具，在隔离环境中修改代码，由独立验证器判断结果，并保存完整执行轨迹与评测数据。

```text
任务与初始仓库
    ↓
创建 Sandbox → 初始化 State → 构建 Context
    ↓
调用模型 → 执行工具 → 返回 Observation → 更新 State / Trace
    ↑                                      ↓
    └──────────── 验证未通过，且未达到限制 ────────┘
                                           ↓
                                  验证通过或终止
                                           ↓
                                  保存结果并清理环境
```

第一阶段的完成标准是**整条链路可重复运行**，而不是 Agent 必须解决所有任务。失败的任务也要有明确的终止原因和可复查的记录。

## 2. 范围与约束

### 本阶段包含

- 一个模型后端接口；先接入一个可用的模型服务，保留替换后端的接口。
- 一个 Agent Loop，以及任务状态、上下文构建、步数与运行时间限制。
- `read_file(path)`、`write_file(path, content)`、`run_shell(command)` 三个工具。
- Docker Sandbox：每个任务使用独立工作区，限制访问范围、运行时间和资源。
- 独立 Verifier：依据测试、构建或输出检查给出成功与否。
- Trace、单任务结果、批量评测脚本与汇总指标。
- 10～20 个可自动验证的 Coding Tasks、使用说明和演示案例。

### 留待后续阶段

错误分类、策略化重试、回滚、重复行动检测属于第二阶段的 Failure Recovery；跨任务持久记忆属于第三阶段。第一阶段仍需处理基本运行错误，例如无效工具参数、命令超时、模型调用失败和达到步数上限，以便系统能安全退出并留下结果。

## 3. 工作节点与验收

每个节点完成后，先保留可运行产物、运行命令和验证结果，再推进依赖它的节点。

### 节点 A：确定任务与模块契约

**状态**：已完成。产物见 [`contracts.md`](contracts.md)、[`coding_agent/contracts.py`](../coding_agent/contracts.py)、[`config/default.json`](../config/default.json) 和 [`tasks/task_001/`](../tasks/task_001/)。

**工作内容**

1. 规定任务包结构：`task.md`、初始 `repo/`、Verifier 及任务元数据。
2. 规定模型输出：工具调用或最终回复；明确无效调用的处理方式。
3. 规定工具结果：成功状态、输出、错误信息、耗时。
4. 规定运行结果：任务 ID、成功状态、终止原因、步数、工具调用、模型用量、耗时、Trace 路径。
5. 建立项目目录、配置文件与一个最小示例任务。

**产物**：接口约定、项目骨架、示例任务。

**验收**：能根据约定清楚回答“任务如何加载、动作如何传递、成功如何判断、结果存在哪里”。

### 节点 B：实现可确定性复现的 Agent Loop

**状态**：已完成。任务加载、State、Context、Runner 和预设模型已实现；用两轮预设动作验证了循环与终止结果。

**工作内容**

1. 实现任务加载、State、Context、动作分发和循环控制。
2. 先使用返回预设动作的假模型，避免真实模型输出影响流程调试。
3. 处理达到最大步数、模型无动作、无效动作和执行异常等终止情况。
4. 为每一步保留最基本的事件记录；完整 Trace 格式在节点 F 固定。

**产物**：单任务 Runner、假模型和可重复运行的流程示例。

**验收**：给定相同示例任务和预设动作，执行顺序、最终状态与终止原因一致。

### 节点 C：接入三个工具与 Docker Sandbox

**状态**：已完成。镜像包含 Python、Git 和 pytest；三个工具已在独立容器中完成读、写、命令执行，运行结束后工作区与容器被清理。

**工作内容**

1. 实现容器创建、任务仓库复制或挂载、命令执行、结果读取和容器清理。
2. 将三个工具统一接入 Runner，使读写和命令操作都指向任务工作区。
3. 对文件路径、命令运行时间、容器 CPU 和内存设置基本限制；不挂载宿主机敏感目录。
4. 保证每次运行从干净的初始仓库开始，任务之间不共享修改结果。

**产物**：Sandbox 管理器、三个工具实现和容器内运行示例。

**验收**：假模型可以在容器中读取文件、修改文件、运行命令；任务结束后容器被清理，下一次运行恢复初始状态。

### 节点 D：接入真实模型

**状态**：已完成。默认接入 DeepSeek V4.1 Flash（`deepseek-flash`）；真实模型完成了读取、修改与独立验证的多轮任务。模型回复中的多个工具调用也可在同轮顺序执行。

**工作内容**

1. 实现统一的 `ModelBackend` 接口，并接入一个实际模型服务。
2. 将任务描述、工具定义和必要的历史观察组织为模型上下文。
3. 解析模型工具调用，把工具执行结果返回给模型，支持多轮操作。
4. 记录模型调用错误和用量；若服务未返回某项用量，结果中明确标为空值。

**产物**：真实模型后端和单任务交互演示。

**验收**：模型能依据任务自行选择工具，完成至少一次“模型调用 → 工具执行 → 模型继续”的往返。

### 节点 E：加入独立 Verifier 与结束判定

**状态**：已完成。Verifier 在独立容器的工作区快照上运行；初始任务失败、修复后通过，模型仅声称完成时仍判失败。

**工作内容**

1. 为任务配置验证方式，例如 `pytest`、构建命令或输出检查。
2. 由 Harness 调用 Verifier；模型的最终回复不能单独作为成功依据。
3. 确保 Agent 不能直接修改用于最终判定的验证逻辑。
4. 明确成功、最大步数、超时、模型错误、工具错误等结束原因。

**产物**：Verifier 接口、至少一个实际验证器、成功和失败案例。

**验收**：同一个任务在初始仓库上验证失败，修复后验证通过；Agent 自称完成但验证未通过时，结果仍为失败。

### 节点 F：完成 Trace 和 Evaluation

**状态**：已完成。单任务产物包含 Trace、结果与配置快照；批量入口生成成功率、平均步数、工具调用与耗时汇总。已用临时结果目录完成端到端检查。

**工作内容**

1. 保存每一步的模型动作、工具参数、观察结果、验证结果和时间信息。
2. 保存单任务结果，包括 `success`、`steps`、`tool_calls`、`failed_tool_calls`、`retries`、`tokens`、`latency` 和终止原因。
3. 实现批量运行入口，汇总成功率、平均步数、平均工具调用次数和平均耗时。
4. 固定任务版本、模型配置和运行参数，使结果有可追溯的实验条件。

**产物**：Trace 文件、单任务结果文件、批量评测脚本和汇总报告。

**验收**：任取一条评测结果，能找到对应任务、配置与逐步执行记录，并解释它为何成功或失败。

### 节点 G：扩充任务集并交付完整项目

**状态**：已建立 10 个任务；每个任务均检查了初始失败与临时修复后通过。预设动作的批量链路检查为 10/10；真实模型实验结果仍待节点 D 的实际服务联通后生成。

**工作内容**

1. 从少量示例扩充到 10～20 个可自动验证任务，覆盖测试失败、配置错误、导入错误、缺失函数和简单 API Bug 等类型。
2. 检查每个任务的初始状态确实未通过验证，预期修复能够通过验证。
3. 批量运行任务集，整理成功率、失败案例和运行限制。
4. 编写 README：环境准备、配置、单任务运行、批量评测、结果查看和演示步骤。

**产物**：任务集、实验结果、README 和可复现 Demo。

**验收**：从项目说明出发，能够运行一个任务和整个任务集，并查看验证结果、执行轨迹及评测汇总。

## 4. 实施顺序

```text
A 接口与示例任务
        ↓
B 假模型驱动的 Agent Loop
        ↓
C Docker Sandbox 与三个工具
        ↓
D 真实模型接入
        ↓
E 独立 Verifier
        ↓
F Trace 与 Evaluation
        ↓
G 任务集、实验结果与文档
```

这个顺序让每次新增能力都有已运行的基础可供验证。节点 B 用确定性输入检查主流程；节点 C 检查真实执行环境；节点 D 再引入模型的不确定性。每个节点的结果都可以单独展示，不需要等全部实现后才知道系统是否能工作。
