# 节点 P：真实基线失败分类

## 范围与方法

分析[节点 O 的 30 次真实模型运行](../../experiments/2026-09-28-real-baseline/report.json)，逐一核对 19 次失败的 Trace、最终 Verifier、补丁和运行结果。每例的任务 ID、运行 ID、失败类别、关键步骤、Trace 行号、最终补丁、观察到的过程及候选恢复点保存在[逐例分类](../../experiments/2026-09-28-real-baseline/failure_taxonomy.json)；[证据清单](../../experiments/2026-09-28-real-baseline/failure_evidence.json)保留从原始产物提取的数值和路径。

主类别按**实际终止机制**划分，每例再标注一个占主导的可见过程模式。预算耗尽说明运行何时停止；模型为何一直没有修改源码，只能根据动作序列描述为“持续诊断、未进入编辑”，不能从 Trace 推断其内部意图。过程模式不是独立根因，候选恢复点是下一轮实验的假设，不是已验证能成功的修复。

## 分类结果

| 主类别 | 次数 | 可直接观察的共同点 |
| --- | ---: | --- |
| Budget Exhaustion | 15 | 均在读源码、查资料或运行探针后达到累计 Token 上限；最终仓库补丁为空 |
| Model Service Failure | 4 | 模型 API 响应截断，Trace 记录 `model_service` 事件；恢复关闭后结束；最终仓库补丁为空 |
| 合计 | 19 | 最终独立 Verifier 均未通过 |

| 任务 | 预算耗尽 | 模型服务失败 |
| --- | ---: | ---: |
| `real_002` | 3 | 0 |
| `real_003` | 3 | 0 |
| `real_005` | 2 | 1 |
| `real_006` | 2 | 1 |
| `real_008` | 0 | 1 |
| `real_009` | 2 | 1 |
| `real_010` | 3 | 0 |

预算失败中进一步观察到以下过程模式。它们按每次运行最突出的动作序列归组，不能与终止原因相加：

| 可见过程模式 | 次数 | 对应任务 |
| --- | ---: | --- |
| 定位源码后继续找历史版本、文档或外部参考 | 3 | `real_002` |
| 继续检查源码、测试和数值格式探针 | 3 | `real_003` |
| 持续调查多个解析文件的规则与测试 | 4 | `real_005`、`real_006` |
| 持续探查流对象和标准库行为 | 2 | `real_009` |
| 持续做跨模块行为探针 | 3 | `real_010` |

**主要失败模式是达到预算之前没有形成源码修改（15/19）。**这 15 次平均执行 9.87 个模型步骤，每次运行的最大输入上下文平均约 24,466 Token，合计发生 27 次上下文压缩事件。Trace 显示其间完成了源码读取和行为探针，但继续诊断直到累计预算检查终止。8/15 次预算失败出现至少一次完全相同的工具调用。上下文压缩和重复动作是伴随现象；目前没有证据把它们判定为独立的“上下文丢失”根因。

## 代表性证据

- [real_002 第 1 次，最后动作第 12 步](../../experiments/2026-09-28-real-baseline/records/20260928T141155-real_002-c59d65bb/trace.jsonl#L48)：已读取 `number.py`、测试并运行数值探针，之后继续查文档和版本；[最终补丁](../../experiments/2026-09-28-real-baseline/records/20260928T141155-real_002-c59d65bb/diff.patch)为空。候选干预点是完成源码和测试定位后的第 5 步。
- [real_009 第 2 次，第 9 步的工具拒绝](../../experiments/2026-09-28-real-baseline/records/20260928T142114-real_009-d7d588de/trace.jsonl#L44)：探查流对象后，尝试用 `write_file` 写工作区外的 `/tmp/patch.txt` 被拒绝；[最终补丁](../../experiments/2026-09-28-real-baseline/records/20260928T142114-real_009-d7d588de/diff.patch)为空。这里还有明确的工具路径误用，但终止机制仍是预算耗尽。
- [real_005 第 1 次，服务错误第 5 步](../../experiments/2026-09-28-real-baseline/records/20260928T141317-real_005-ca1326cc/trace.jsonl#L30)：需求与标记探针之后，下一次模型响应截断；[最终补丁](../../experiments/2026-09-28-real-baseline/records/20260928T141317-real_005-ca1326cc/diff.patch)为空。候选恢复点是保留当前状态并有限重试该模型请求。

19 次失败中，17 次出现工作区路径拒绝，14 次尝试过 Git Shell 命令。成功的 11 次中对应也有 10 次和 8 次，因此这些现象不能单独解释失败。评测任务的源码副本没有 Git 历史；`DockerTools` 要求文件工具使用相对路径。模型实际可调用的只有 `read_file`、`write_file`、`run_shell` 三种工具：`run_task` 未传入扩展工具清单，Runner 使用默认 `TOOL_SPECS`，30 次 Trace 也只有这三种工具名。较完整的仓库工具虽有实现，本次基线没有测到它们的效果。[节点 O 记录](节点O-真实模型基线实施记录.md)已更正这一实验范围。

## 后续实验的依据

下一阶段可用**相同的三工具任务配置**比较 Recovery OFF/ON，重点检查响应截断后能否继续、无效工具调用能否减少，以及“未编辑即耗尽预算”是否仍存在。恢复策略对服务错误提供有限重试，但能否提高最终成功率必须由成对实验验证。

若要评估完整仓库工具、分段读取或促使更早编辑的策略，应另设实验，并为该工具集重新运行 OFF 基线；不能把它与本次三工具基线直接比较。P 阶段的 19 个失败案例均已分类，每类有可定位的 Trace，主要失败模式和可检验的后续假设已明确。
