# 节点 Q：Recovery 真实任务对照

## 实验设计

2026-09-29 对节点 N 的 10 个真实仓库任务各做 3 轮 Recovery OFF/ON 配对，共 30 对、60 次运行。每轮同一任务各运行一次，奇数轮 OFF 先、偶数轮 ON 先。两组使用相同任务快照、模型、三种基础工具、预算、超时和容器镜像；逐对保存的 `config.json` 经核对仅有 `recovery.enabled` 不同。Memory 和 Parallel 均关闭，无人工介入。

运行代码提交为 `d5ee619`，固定任务摘要和配置见[实验清单](../../experiments/2026-09-29-real-recovery/manifest.json)与[配置文件](../../config/real-recovery-2026-09-29.json)。预算为 80 步、120,000 个已知 Token，单任务超时 1,800 秒；容器镜像 ID 为 `sha256:4217cbc4df372b696f659c9f25d32dccbc52b4c33ddb8e8c2008c0aa8ae1f163`，1 CPU、512 MiB、容器断网。模型为 `deepseek-flash`；运行前后接口均返回 DeepSeek-V4.1-Flash，见[版本检查](../../experiments/2026-09-29-real-recovery/api_model_checks.json)和[服务商更新记录](https://api-docs.deepseek.com/updates/)。服务端别名没有不可变权重修订号。

实验使用与节点 O 相同的三工具范围：`read_file`、`write_file`、`run_shell`。当前任务评测入口没有接入文件快照回退，因此 ON 在这里实际可触发的是模型服务重试、只读工具超时重试、失败后指导、重复失败动作拦截和最终验证重试。实验没有改变这些机制本身。

## 结果

| 指标 | Recovery OFF | Recovery ON | ON − OFF |
| --- | ---: | ---: | ---: |
| 任务通过 | 15/30（50.0%） | 11/30（36.7%） | −4 次，−13.3 个百分点 |
| Token 预算终止 | 13 | 19 | +6 |
| 模型服务错误终止 | 2 | 0 | −2 |
| 平均步数 | 8.97 | 9.87 | +0.90 |
| 平均工具调用 | 13.10 | 13.90 | +0.80 |
| 平均失败工具调用 | 2.30 | 2.43 | +0.13 |
| 平均完全相同的重复工具调用 | 0.90 | 0.83 | −0.07 |
| 平均耗时 | 36.21 秒 | 35.90 秒 | −0.31 秒 |
| 人工介入 | 0 | 0 | 0 |

30 对中，双方都通过 7 对，仅 ON 通过 4 对，仅 OFF 通过 8 对，双方都失败 11 对。[派生分析](../../experiments/2026-09-29-real-recovery/analysis.json)记录了逐题结果和配对差值。以任务为单位对三轮配对做 20,000 次重抽样，成功率差的探索性 95% 区间为 **−33.3 至 +3.3 个百分点**。本样本没有显示 Recovery 提高成功率；样本小，不能据此断言它在其他任务上必然降低成功率。节点 O 的旧 OFF 批次为 11/30，本轮重新运行的 OFF 为 15/30，也显示了直接引用旧批次作为本轮对照的风险。

Token 用量有 3 对不完整：OFF 两次、ON 一次发生无法计量用量的模型服务请求，最终 `tokens` 为 `null`。在另外 **27 对可完整计量**的运行中，OFF 平均 98,479 Token，ON 平均 110,911 Token，ON 每对平均多 **12,432 Token（约 12.6%）**；任务级重抽样的探索性 95% 区间约为 +5,841 至 +18,843 Token。这个成本比较不包含三对缺失值，也不包含失败请求未返回的用量。Token 预算在每轮模型请求前检查，单轮后累计值可以超过 120,000；服务错误请求的未知用量也无法计入已知预算。延迟的配对均值差为 −0.31 秒、中位数差为 +2.27 秒；对应重抽样区间约为 −5.41 至 +3.66 秒，未观察到稳定的延迟方向。

## 恢复轨迹与边界

ON 组记录了 71 次 `alternative_action` 事件、73 条失败后指导，以及 **1 次** `model_retry`；没有 `tool_retry`、`repeat_block`、`validation_retry` 或 `snapshot_rollback`。`alternative_action` 表示失败后下一次工具调用不同，不能单独算作任务被恢复。ON 组的 11 次通过都发生在有工具失败记录的会话里，但 OFF 组也有 15 次这样的通过，不能从这些计数推断指导带来的因果收益。

- **失败后完成任务的 ON 案例**：[real_003 第 3 轮 Trace](../../experiments/2026-09-29-real-recovery/records/20260929T050630-real_003-d2c72408/trace.jsonl#L42)在工具失败与指导后改用 Shell 编辑源码，独立 Verifier 随后通过；对应 OFF 达到预算。它是可观察的成功轨迹，不能证明 ON 的指导导致了配对差异。
- **模型重试后仍失败的案例**：[real_002 第 2 轮 Trace](../../experiments/2026-09-29-real-recovery/records/20260929T045247-real_002-a4a25893/trace.jsonl#L47)在响应截断后进行一次重试，模型继续返回动作，但第 9 步后达到 Token 预算，最终补丁为空。服务请求恢复率在这唯一一次事件中为 1/1，任务成功率为 0/1。
- **ON 未解决预算失败的案例**：[real_007 第 2 轮 ON Trace](../../experiments/2026-09-29-real-recovery/records/20260929T045807-real_007-c433dde1/trace.jsonl#L63)在 12 步后耗尽预算、补丁为空；[对应 OFF Trace](../../experiments/2026-09-29-real-recovery/records/20260929T045828-real_007-449d0d20/trace.jsonl#L51)在第 8 步修改源码并通过。`real_006`、`real_010` 两组各三轮均未通过。

OFF 有两次因响应截断终止，分别发生在 `real_004` 第 1 轮和 `real_008` 第 3 轮；同对 ON 虽通过，却没有发生模型服务重试。这两次配对差异不能作为重试奏效的证据。本轮没有过量重试：仅一次模型重试，低于配置上限。ON 的 19 次预算失败均无最终源码差异，说明当前恢复动作没有解决节点 P 识别出的主要“未编辑即耗尽预算”模式。

## 产物与结论

[原始报告](../../experiments/2026-09-29-real-recovery/report.json)包含 60 次结果和 30 对配对关系。每次运行均保存 Trace、Diff、最终检查、结果和配置，共 300 个核心文件。审计确认配置只差 Recovery 开关、每份 Trace 的终态与结果和检查一致、全部非空补丁能应用到对应基线。临时检查脚本没有进入工程。

在这组三工具真实任务中，当前 Recovery ON **没有提高总体成功率**，并在可完整计量的配对中增加了 Token 用量。它能让一次截断的模型请求继续，但未把该任务转为成功；对反复诊断直至预算耗尽的失败模式没有观察到收益。后续若改进工具集、路径说明、上下文或编辑时机，应另设受控实验并重新建立匹配的 OFF 基线。
