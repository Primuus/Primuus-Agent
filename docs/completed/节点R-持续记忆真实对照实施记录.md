# 节点 R：Persistent Memory 真实对照实施记录

## 实验设计

2026-09-29 在同一个 `python-humanize/humanize` 仓库上依次执行五个上游真实修复任务：`intcomma` 大整数、`metric` 舍入进位、`natural_list` 可迭代输入、`intword` 舍入进位和 `naturaldelta` 年数舍入。[任务清单](../../tasks/memory_real/humanize-series.json)固定任务文本、上游基线、后续提交、项目检查和独立隐藏断言。预检确认每题的断言在修复前失败，在对应上游修复后通过。

每题分别运行 Memory OFF、Summary Memory 和 Retrieved Memory，模式顺序逐题轮换。三组从同一代码提交起步，使用独立记忆库；一题结束后统一应用上游代码变更，再执行下一题。因此这里比较的是**同一持续演进仓库上的跨会话记忆**，没有把某组 Agent 的补丁传给下一题。起始记忆为空，Summary 取最近条目，Retrieved 按任务词和路径重合度选择条目；两组按现有 Runtime 规则自动捕获记忆，没有人工注入有益提示。

基于[配置](../../config/real-recovery-2026-09-29.json)，Recovery 关闭，预算为 80 步、120,000 个已知 Token、每题 1,800 秒；仓库会话使用完整仓库工具集，与 O/Q 阶段的三工具入口不同，成功率不能直接跨阶段比较。Docker 镜像 ID 为 `sha256:4217cbc4df372b696f659c9f25d32dccbc52b4c33ddb8e8c2008c0aa8ae1f163`，1 CPU、512 MiB、容器断网。模型别名为 `deepseek-flash`，运行前后接口均列出该模型；[DeepSeek 更新记录](https://api-docs.deepseek.com/updates/)将它对应到 V4.1-Flash。每题每模式只运行一次，以下为描述性比较。

实验入口提交为 `5db3dd2`。首轮审计发现 Agent 可通过完整上游 Git 历史看到未来修复提交，因此该轮作废；`bdbfe20` 改为只向 Agent 暴露已到达的本地历史。隔离重跑在第一题后遇到生成接口 HTTP 402；`635bf8c` 增加不可重试服务错误即停与续跑能力。额度恢复后从第二题继续，14 条零步服务失败不计入结果。最终[审计文件](../experiments/2026-09-29-real-memory/audit.json)确认 17 个有效会话使用了对应相同基线和非记忆配置，未来上游修复对象不可见，6 个非空补丁均能应用到各自基线；17 个最终工作区的隐藏断言在 Agent 所用 Docker 镜像中重放，与主机判定全部一致。

“仓库探索调用”包括 `list_files`、`search_text`，以及 Shell 中的目录搜索和 Git 历史/状态查询；跨题重复探索按标准化命令完全相同计数。“重复显式文件读取”指本次 `read_file` 或 `read_file_range` 读取此前同模式任务读过的路径，Shell 内的文件读取未计入，因此是下界。“首次有效编辑时间”指首次成功执行、且目标路径出现在最终补丁中的写入操作；它是 Trace 代理指标，仅在有可观测编辑的运行上计算。会话耗时不含外部隐藏验证。

Summary 最终只产生 3 条失败记忆，Retrieved 只产生 2 条失败记忆，**没有项目知识或已验证修复记忆**。所有项目检查都未触发，现有捕获规则无法把虽已通过隐藏验证但未正常收尾的修复写成 Fix。Retrieved 在第二题通过时所选记忆为 0 条；Summary 在第一题通过时也没有记忆。因此这组成功率和探索次数差异不能归因于 Persistent Memory。Retrieved 的跨题重复文件读取与完全重复探索调用反而最多，未观察到稳定的“减少重复探索”效果。当前最直接的瓶颈是 Agent 修好代码后仍继续调用工具，直到预算耗尽。

## 错误记忆探针

在第四题相同代码基线和原始任务文本上，从该题开始前的记忆快照分别注入一条错误项目记忆：声称 `intword` 的实现位于 `src/humanize/lists.py`，而 `src/humanize/number.py` 已正确。两个模式都选中了该条记忆。Summary 的正常运行与污染运行均未通过；Retrieved 的正常运行未通过，污染运行却通过，并在 `src/humanize/number.py` 作出有效修改。错误条目没有让这次 Agent 放弃核对当前源码，但单次结果不能证明它无害，也不能把污染运行的成功归功于错误记忆。探针与主对照分开统计。

## 结论与后续依据

节点 R 的五题同仓库任务、三模式对照、重复探索指标、成本记录和错误记忆探针均已完成。当前实现确实把历史条目送入上下文，但本轮没有形成可复用的项目/修复记忆，也没有足够证据显示它提高成功率或持续减少探索。每题每模式只有一次运行，模型响应截断和三组在首题均无记忆进一步限制了因果解释。

下一阶段的 Runtime 收敛应优先处理“已正确编辑却不收尾”的路径，并让项目检查和记忆捕获在真实任务中形成闭环；随后再以相同任务链重复评估记忆机制。此次没有为这些发现增加永久测试脚本，实验所需的任务断言保存在任务清单中，原始会话产物留作审计。
