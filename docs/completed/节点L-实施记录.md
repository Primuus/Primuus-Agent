# 节点 L 实施记录

节点 L 的目标是让模型与外部能力通过清晰的入口接入普通仓库会话。各小目标验证后分别提交；节点完成时再做一次整体汇报。

| 小目标 | 内容 | 当前状态 |
|---|---|---|
| L1 | Anthropic Messages 模型适配；项目 `AGENTS.md`、额外指令文件与显式选择的技能进入会话上下文 | 已完成 |
| L2 | 在隔离工作区执行可配置 Hooks；沿用写入与命令权限，并记录执行事件 | 已完成 |
| L3 | 使用官方 MCP 客户端接入外部工具；工具发现、调用和权限共用现有会话接口 | 已完成 |
| L4 | 提供适合 CI 使用的入口和稳定产物；验证交互与无交互会话记录 | 已完成 |

## L1 验证

- 模拟 Anthropic Messages API 响应，确认系统消息、历史工具调用及结果的转换和工具动作解析。
- 在临时 Git 仓库创建会话，确认 `AGENTS.md` 与所选技能写入事件，重新加载后仍进入模型上下文。
- 项目原仓库保持不变；验证未留下临时测试文件。

后续小目标继续沿用 Session Runner。扩展的执行结果进入原有工具观察和事件记录。

## L2 验证

- 在临时 Git 仓库中运行 Docker 会话，确认工具前后 Hook 均通过权限询问执行，结果与人工介入次数写入 Trace；重新加载会话后事件保持一致。
- 前置 Hook 失败时，原工具不执行，模型得到错误观察。临时验证文件已清理。

## L3 验证

- 使用 MCP Python SDK 2.2 的本地 stdio 服务验证工具发现、参数描述和调用结果。模型在普通 Git 仓库会话中看到新工具，结果进入下一轮上下文与 Trace。
- 同一服务分别验证 `ask` 模式只询问写操作、`read-only` 模式拒绝写操作；拒绝后服务未收到调用。配置中仅按名字选择需要传给服务的环境变量。
- 验证脚本和仓库由临时目录生成并清理；MCP SDK 装于临时目录，工程默认安装不依赖 SDK。

## L4 验证

- `ci` 调用普通仓库会话，不新增 Agent Loop；明确指定产物目录，保存摘要、完整结果、Trace、补丁及工作区状态。CI 禁用询问式权限，使用 0/1 退出码给流水线判定。
- 通过本地临时模型 HTTP 服务和临时 Git 仓库运行成功与项目检查失败两种场景：成功退出 0，失败退出 1，两者均生成相同的五类产物。验证目录结束后清理。
- 同一临时模型服务下分别运行 `chat` 和 `ci`，确认两者均记录 `user_message`、`model_action`、`task_finished` 与 `run_duration`，并采用同一个 Session Runner。
- 增加手动触发的 GitHub Actions 工作流，使用仓库密钥、Docker 隔离工作区和产物上传。工作流配置完成静态检查；尚未在 GitHub 托管运行器上触发真实模型任务。

节点 L 的四个小目标均已通过局部验证并分别提交。模型、指令、Hooks、MCP 与 CI 入口都沿用普通仓库会话的 Runner、权限和事件记录。
