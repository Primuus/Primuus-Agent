# Long-Horizon Coding Agent 总体方案

> 本文是第一阶段完成后的后续执行依据。按能力节点和验收结果推进，不按时间安排。第一阶段的详细过程保留在[第一阶段执行方案](Long-Horizon-Coding-Agent-Phase-1-Execution-Plan.md)；早期[项目初稿](Long-Horizon-Coding-Agent-Execution-Plan-Draft.md)作为历史背景。后续如有范围调整，先更新本文，再实施对应节点。

## 1. 目标与定位

最终交付一个自研、可实际处理代码仓库任务的 Long-Horizon Coding Agent。它应具备主流 Coding Agent 的基本工作能力：理解仓库、交互式讨论与规划、搜索和精确修改代码、运行命令与项目检查、审阅变更、管理权限、保存和恢复会话，并提供可扩展的工具与模型接口。在此基础上研究失败恢复、上下文管理、持久记忆等长任务机制。

项目同时服务两个场景：

1. **日常开发**：用户指定仓库与目标，Agent 在隔离工作区中完成修改，留下可审阅的 diff、检查结果和说明。
2. **可重复研究**：同一执行内核运行固定任务集；记录模型、任务版本、配置、轨迹和结果，用相同条件比较新增机制。

产品使用与实验评测共享 Session Runner、工具和工作区实现。任务包和独立 Verifier 是评测入口，不应成为日常使用入口的前置条件。

## 2. 当前基础与差距

第一阶段 A～G 已完成：Agent Loop、模型适配接口、三个基础工具、Docker Sandbox、独立 Verifier、Trace、批量评测和最初 10 个小型任务。默认模型为 DeepSeek V4.1 Flash（`deepseek-flash`），服务地址为 `https://api.deepseek.com`。一次真实模型批量运行的结果为 10/10；每题只运行一次，结果仅作为这 10 题的基线。详情见[实验报告](experiments/2026-09-26-deepseek-flash/README.md)。

节点 H～J 已把同一 Runner 扩展到普通 Git 仓库会话，具备持久工作区、运行中事件记录、计划、快照和续跑。节点 K 补上失败分类、有限重试、重复动作拦截、项目检查后的再修复与成对评测入口；任务集扩至 12 题。[受控故障注入报告](experiments/2026-09-27-recovery-controlled/README.md)验证了机制链路，尚不能代表真实模型在一般仓库任务上的收益。

## 3. 目标使用流程

```text
选择现有仓库并提出任务
    ↓
读取项目指令、Git 状态与相关代码
    ↓
必要时形成计划并与用户对齐
    ↓
在隔离工作区搜索、修改、运行检查
    ↓
展示进度、错误、检查结果和 Git diff
    ↓
继续修改 / 暂停续跑 / 完成交付
```

简单任务可以直接执行；复杂任务使用可更新的计划。用户始终可以查看当前变更、给出新指令、暂停会话或结束任务。交付至少包含变更摘要、相关检查结果、未解决的问题和可审阅的 diff。

## 4. 架构边界

```text
交互 CLI / 无交互 CLI / 后续 IDE 或服务入口
                    ↓
Session Runner：状态、计划、事件、权限、预算、暂停与恢复
                    ↓
Model Adapter ─ Context Manager ─ Tool Registry
                    ↓
持久工作区 / Sandbox ─ 项目检查 ─ Git 差异与快照
                    ↓
运行记录与结果；Evaluation 使用同一 Runner 批量调用
```

- **Session**：以仓库、用户目标、模型、运行配置和权限为输入；保存当前计划、进度、事件序列、工作区引用和终止原因。事件在执行过程中持续落盘，支持进程退出后的恢复。
- **Workspace**：使用独立的 Git worktree 或等效隔离副本，保留用户原仓库状态；记录基线提交和当前 diff。快照用于回退与续跑，工作区生命周期独立于单次进程。
- **Runner**：负责模型轮次、工具分发、状态更新、预算和中断。模型、工具、工作区及验证均通过明确接口接入；评测模块不再负责组织主执行流程。
- **Context Manager**：按需纳入项目指令、相关代码、近期对话、计划和检查结果；旧轨迹可摘要，关键事实保留来源。跨会话记忆另行实现，避免把摘要当作可信的永久知识。
- **Checks / Verifier**：日常运行执行项目测试、构建或用户指定命令；评测运行独立 Verifier。检查在修改后、里程碑或结束前按需触发，不固定在每一轮工具调用之后。
- **Permissions**：按读、写、命令、网络和外部系统操作定义允许、询问或拒绝规则。模型密钥留在运行环境，不进入工作区、Trace 或仓库。

优先保证单 Agent 路径可靠。多 Agent、自动技能学习和图形界面建立在稳定的会话、权限和工作区接口上。

## 5. 能力节点与验收

### 节点 H：通用会话内核

**状态**：已完成。评测任务通过通用 Session Runner 执行；会话状态统一记录用户消息、模型动作、工具结果、验证结果和结束事件。已重放 10 条基线轨迹，全部通过。

**任务**：从现有任务评测入口抽出通用 Session Runner；定义 Session、事件和工作区接口。现有任务加载器作为适配器调用新 Runner，保留既有模型、工具、Verifier 和评测口径。

**验收**：日常任务与现有任务包走同一执行内核；原有 10 个任务的基线行为可复查；模型动作、工具结果和结束原因都有稳定的事件记录。

### 节点 I：真实仓库的基本 Coding Agent

**状态**：已完成。支持普通 Git 仓库的交互式和无交互任务；会话使用独立持久副本，提供文件发现、搜索、分段读取、精确编辑、Shell、Git 状态与差异、权限模式和项目检查。工作区与审阅产物在进程结束后保留。

**任务**：提供交互式会话与无交互入口；支持文件发现、内容搜索、分段读取、精确补丁、Shell、Git 状态与 diff；在持久隔离工作区执行，并提供基础权限策略与变更审阅。

**验收**：对一个普通现有仓库完成需要跨文件修改的任务，用户可查看完整 diff 与检查结果；原仓库已有的未提交改动不被覆盖；会话结束后成果仍可取回。

### 节点 J：长任务持续执行

**状态**：已完成。会话事件逐条落盘，可从事件恢复对话、计划、用量和工具执行状态；工作区保留 Git 快照，支持暂停、检查、恢复和回退。模型可维护里程碑计划，历史消息超限后压缩为带事件记录的摘要。中断中的工具调用需要先检查工作区并确认，恢复时不自动重放。

**任务**：持续保存事件与状态，加入计划和里程碑、工作区快照、暂停与恢复、上下文压缩和运行预算。恢复时先对齐已完成操作与当前工作区，再继续下一步。

**验收**：在多文件任务进行中终止进程，重新启动后从原工作区和正确进度继续；不会重复执行已完成的有副作用操作；长对话仍能获取完成任务所需的关键信息。

### 节点 K：失败恢复与质量评测

**状态**：已完成。模型服务、工具、命令、构建、测试和最终验证失败分别记录；可重试的模型错误与只读工具超时有限重试，重复失败动作会被拦截，写入、构建和测试失败可回退到操作前快照。普通仓库的项目检查可以触发再修复，检查命令随会话保存。新增两个跨文件任务和成对对照入口；受控故障注入、普通 Git 仓库暂停续跑场景及 10 题历史轨迹重放已验证。真实模型的重复对照仍需运行时密钥与更多仓库样本，不能从受控实验推断一般成功率。

**任务**：区分模型服务、工具、命令、构建、测试和验证失败；加入有边界的重试、重复行动识别、替代行动及快照回退。扩充真实仓库、多文件和中断恢复任务集。

**验收**：在相同模型、任务、预算和验证条件下比较基础版本与恢复版本，报告成功率、恢复率、步骤、用量、耗时和人工介入；失败案例可从轨迹定位原因。

### 节点 L：扩展与集成

**进度**：模型适配已扩展到 Anthropic Messages API，普通仓库会话可加载项目指令和显式选择的技能，来源随会话事件保存。Hooks、MCP 与工作流入口仍在实施中；具体拆分见[节点 L 实施记录](节点L-实施记录.md)。

**任务**：完善模型提供方适配；接入项目指令、可配置技能、Hooks 与 MCP；提供 GitHub/PR 或 CI 等工作流入口。所有扩展通过权限和事件接口运行。

**验收**：至少一个外部工具或标准工作流可被安全接入，不需要改动 Runner 主循环；交互式与无交互模式产出一致的会话记录。

### 节点 M：持久记忆与并行能力

**任务**：为项目知识、历史失败和有效修复建立有来源、适用范围与更新机制的持久记忆；按需检索到 Context。多 Agent 使用隔离工作区和明确的任务交接。

**验收**：在可重复的跨任务实验中比较无记忆、摘要记忆和检索记忆；并行任务的代码修改与结果能够独立审阅和整合。

节点 H～J 形成可日常使用、可续跑的产品基础；节点 K～M 在同一基础上扩展研究能力。每个节点完成后保留可运行产物和验收记录，提交并推送仓库，再推进下一个节点。

## 6. 评测原则

- 保留第一阶段小任务作为回归基线，同时增加真实仓库、多文件修改、功能开发、配置/依赖、长任务中断与恢复等任务。
- 任务初始状态、参考修复路径和独立验证器应分别核查。评测 Verifier 不暴露给 Agent。
- 比较机制时固定模型版本、任务版本、运行预算和环境；记录每次运行的配置与完整轨迹。模型结果有随机性，重要结论使用重复运行，不以单次 10/10 推断一般成功率。
- 除成功率，还记录最终 diff 的可审阅性、回归情况、续跑正确性、失败恢复率、人工介入、Tokens、耗时和工具调用。
- 只保留有验证价值的测试与任务 Verifier。临时测试文件在验证后删除；工程运行和构建不依赖临时测试文件。

## 7. 实施约束与文档位置

- 按节点交付并提交；每次提交说明完成内容、验证方式和剩余限制。
- 每完成两个后续节点（H/I、J/K、L/M），复查测试性质的脚本；没有运行依赖或评测价值的脚本及时删除。现有 10 个任务的 `verifier.py` 仍用于评测，按任务数据保留。
- 遵守已有工程风格，避免无依据的防御性分支、静默兜底和冗余测试。权限隔离、清晰错误语义与必要的失败处理属于产品功能。
- `docs/` 只存放项目方案、接口说明、使用说明和实验报告等文档。源代码、任务、生成的原始结果和 Trace 分别放在代码目录、`tasks/`、运行目录或仓库根部的实验产物目录；报告链接到相应产物。
- 默认使用运行时环境变量提供模型密钥；密钥不进入配置文件、文档、运行结果或 Git 历史。
