# 节点 S：Runtime 工程收敛进度

## S1：项目检查记录一致性

2026-09-30 对 `745057c` 的修复继续收敛。发现编辑后项目检查通过、最终答复复用检查结果时，重新加载只读取最终答复之后的检查事件，导致检查记录丢失。在旧代码副本中复现：会话正常结束，检查执行两条，加载前 `checks` 为两条，加载后为零条。

本节点将项目检查命令集、最近完整检查和补丁 SHA-256 纳入会话状态。开始、逐命令结果、完整批次分别写入事件，最终答复无需重复执行相同检查即可恢复记录。失败后再次修复只展示最近批次；新任务、命令集变更和恢复快照清空旧检查。`checks_current` 只说明检查是否对应当前补丁，检查成败仍由退出码判断。续跑最终答复时重新验证工作区，防止外部改动后直接沿用成功终态。检查命令若改变补丁，该次验证不通过；不匹配当前补丁的结果不会用于写入成功记忆。

### 针对性验证

使用项目已有的 ScriptedBackend、真实 Git 副本和固定 Docker 镜像验证四条路径。脚本与样例仓库放在临时目录，验证后删除，工程没有导入或依赖临时脚本。

| 场景 | 结果 | 关键证据 |
| --- | --- | --- |
| 编辑后检查、直接收尾、重新加载 | 通过 | 两条检查各执行一次，加载后仍为两条；保留 Project/Fix 记忆 |
| 首次检查失败、再次修复、恢复快照 | 通过 | 失败输出反馈模型；最后两条检查通过；恢复快照后检查清空 |
| 正常完成后外部修改、续跑 | 通过 | 检查标为不对应当前补丁；续跑重新检查并以 `final_unverified` 结束 |
| 检查命令改动补丁且退出码为零 | 通过 | 验证仍失败，不写入 Project/Fix 记忆 |

旧版本复现和四场景报告见 [baseline-reproduction.json](../experiments/2026-09-30-runtime-convergence/baseline-reproduction.json)、[focused-report.json](../experiments/2026-09-30-runtime-convergence/focused-report.json)。这证明上述状态流转符合预期，尚不能证明真实模型会及时收尾或提升任务成功率。

## S2：代表性真实任务复测

使用节点 R 中的 `natural_list_iterables`、`intcomma_overflow`、`intword_rounding_carry`，最多各运行一次，Recovery 与 Memory 均关闭。沿用固定代码基线、原任务文本、项目检查、独立隐藏断言和预算。复测代码为 `3768e05`，模型 ID 为 `deepseek-flash`，预算为 80 步、120,000 个已知 Token；Docker 镜像沿用阶段 R 的固定 SHA-256。接口当时列出了该模型 ID，但不能冻结云端权重版本。

一次复测通过要求：正常 `completed`、当前补丁的项目检查通过、独立隐藏断言通过。功能正确但预算耗尽也记为本轮未通过。若累计两个任务未通过，停止剩余任务与后续 Memory 扩展验证，记录本轮失败。该规则用于有限样本的工程准入判断，不推断未运行任务一定失败，也不用于统计机制收益。

### 剩余问题与下一步

检查触发和记录恢复已经在三个真实任务中观察到有效；预算提示尚不足以保证正常收尾。两个未完成任务均在第 11 轮才有效编辑，最后一次请求使累计用量越过 120,000。Runtime 随后执行了编辑和项目检查，但下一轮立即以 `token_budget` 结束，没有留下最终答复的预算。它们在第 9 轮之前收到过 60% 用量提示，仍继续诊断。逐轮 Token 和动作见 [sample-analysis.json](../experiments/2026-09-30-runtime-convergence/sample-analysis.json)。

两个任务最后一次请求的输入分别为 18,178 和 19,003 Token。后续应优先减少长期保留的大段文件与命令输出，并明确分配定位、编辑、检查和最终答复的预算；继续添加提示或增加重试次数缺少依据。检查通过不应自动代替任务完成确认。

本轮仅做有限样本工程筛查，没有修复前后的同期成对实验，不能将成功率差异归因于某一项改动。临时真实复测脚本、参考仓库和 Agent 工作区均已清理，仅保留审计产物。节点 S 尚未整体验收，当前未执行完整回归集。
