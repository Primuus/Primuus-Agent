# 子问题执行与项目检查复用

## 目标与依据

上一轮 intword 通过，但跨文件仍没有编辑；两题都没有使用计划工具。跨文件已经复现第一个问题，却继续调查其他需求，九次带工作记录的压缩中六次缺少可容纳的源码快照。intword 同一任务还执行了多次配置检查。接下来先落实当前子问题，再减少重复检查，只复测一个跨文件真实任务。

## 计划初始化

- 普通仓库任务开始时，用一次无工具请求生成结构化计划：每项记录需求、状态、文件、未验证假设和下一动作；第一项执行中，其他项待处理。简单任务只需一项。
- 该请求使用同一模型，最多 1,536 输出 Token，计入原来的步数、用量、超时和 Trace。DeepSeek 使用既有无工具请求的 none 推理配置，不使用思考模式不支持的强制工具选择。[官方接口说明](https://api-docs.deepseek.com/api/create-chat-completion/)
- 初始化只生成计划，不能作为任务完成。后续正常工作提供全部工具，在接近当前对话的系统上下文中展示当前子问题，要求定位后先修改、确认行为，再切换独立需求。
- 计划中的目标文件进入现有源码快照保留优先级；路径与假设仍需现场确认。大范围输出仍可能超出保留容量，这个限制没有因计划初始化自动消失。
- update_plan 与初始化共用字段校验；未完成需求中只允许一项执行中。新任务清除旧计划，续跑保留原计划。
- 如果中断发生在计划响应保存后、计划写入前，恢复时直接解析已经保存的响应，不再调用模型。计划响应不进入完成任务的快捷分支。
- 格式错误明确停止并记录，不能靠修补 JSON、猜测字段或隐藏重试生成另一个计划。

定向验证覆盖计划初始化到正常工具请求、用量计入、未完成计划收尾、日志重建、初始化中断恢复和新任务切换。证据：[focused-planning.json](../experiments/2026-10-08-task-focus/focused-planning.json)。尚未执行新的真实任务，节点 S 仍未整体验收。

## 项目检查复用

- 新增 run_checks，只运行用户配置的项目检查；默认复用本次执行中相同补丁的已通过结果，force=true 明确重新执行。返回内容标明实际执行或缓存复用，Trace 记录 project_check_reused。
- 普通 Shell 和 hook 的 Shell 调用在执行前使检查缓存和当前检查元数据失效；只读工具、计划更新和缓存检查读取保留结果。源码补丁变化仍触发自动检查，失败结果不会被复用。
- 最终验证使用同一缓存，避免模型调用 run_checks 后又重复执行同一套检查。不同运行之间启动了新的容器环境，不继承上一次运行的内存缓存。
- run_checks 遵循写操作权限；没有配置检查时返回明确错误。复现脚本与配置检查分开执行，避免普通 Shell 输出被误当成结构化项目检查记录。
- 事实摘要保留历史自动检查证据，分别记录当前检查与之前执行过的检查，防止缓存失效后声称没有运行过测试。

两个临时 Docker 场景验证了缓存读取、强制执行、Shell 与 hook 失效、最终验证复用和日志重建；另确认只读模式阻止显式检查工具。证据：[focused-check-reuse.json](../experiments/2026-10-08-task-focus/focused-check-reuse.json)。场景数据保留为 JSON，临时工作区已经删除，没有永久测试脚本。

## 有限真实验证

实现并提交上述两部分后，只运行 boltons 跨文件一次，固定原任务、源码树、镜像、模型、80 步和 120,000 Token。通过需满足目标源码补丁、当前配置检查、独立行为验证、状态重建及计划完成。失败即停止扩大验证，单次成功也不代表节点 S 整体验收。

## 初始化衔接修正

`387cf1e` 的首次真实尝试生成了三项计划，已知用量为 289 输入、321 输出 Token，但第一次工作请求返回 HTTP 400。没有源码工具调用和修改，独立验证失败，属于启动故障样本。该错误没有记录响应正文，所以不能声称已经取得服务器的具体错误说明；总用量保持 null，不把已知的 610 Token 当成完整成本。原始记录保留在 [report.json](../experiments/2026-10-08-task-focus/real/report.json)。

请求中的无工具、关闭推理的计划 JSON 被作为普通 assistant 消息带入后续思考工具请求，却没有 reasoning_content。根据 [DeepSeek 消息要求](https://api-docs.deepseek.com/guides/thinking_mode/)，这是明确的消息衔接缺陷，能够导致 HTTP 400。

修正如下：

- 计划生成响应保留在 Trace 和用量中，标记为行政步骤，不进入工作对话；计划仍作为结构化状态提供。恢复也重建这个标记，复用已有计划响应。
- 当前子问题提示放在系统上下文中，首次正常工作对话结束于原始用户任务，不用计划 JSON 模拟正常工具轮次。
- 非思考请求明确记录空推理字段，正常工作轮次仍原样保留完整 reasoning_content。
- 初始化也接收已加载的项目与 Skill 指令。
- HTTP 服务错误记录有限长度的响应正文并遮蔽当前密钥，避免下次只得到状态码。

定向验证覆盖实际适配器序列化、行政响应隔离、原始工作推理、初始化恢复、用量与日志重建、项目指令，以及 HTTP 错误中的密钥遮蔽。证据：[focused-handoff.json](../experiments/2026-10-08-task-focus/focused-handoff.json)。没有再次调用真实模型。

首个样本尚未进入源码调查。修复后仅重测同一任务一次，不扩展任务集；启动故障和修复复测分别保留，复测失败后停止。

## 取消累计 Token 上限

按用户要求，默认配置与当前真实任务配置改为 `max_tokens: null`。无累计 Token 上限时，Runner 不按已用或预估 Token 提前收尾；用量、未知服务用量和输入预估仍进入记录。单次工作输出上限为 8,192，行政回顾输出上限为 1,536；任务的轮数与超时单独控制执行。

编辑前行动回顾改用独立配置 `action_review_after_tokens: 40000`，达到阈值只更新下一动作，不停止任务。这样取消总上限后仍能执行最新行动回顾。定向模拟验证确认用量超过旧的 120,000 后仍继续工作，所有剩余 Token 字段为 null，保留行动回顾与日志重建，未完成任务仍不能声明完成。证据：[focused-unlimited.json](../experiments/2026-10-08-unlimited-tokens/focused-unlimited.json)。

下一次仅复测同一跨文件任务一次，保持 80 轮与 1,800 秒任务配置，使用无累计 Token 上限和最新行动回顾；通过仍需当前项目检查、独立行为验证、目标补丁、计划完成与日志重建。失败后停止扩展任务集。本次配置不同于先前有预算样本，不能作为相同预算下的成本或成功率对照。

## 同一文件多次编辑的摘要修正

真实最终答复错误声称只观察到切片修改，插入与 pop 没有编辑证据；也将历史项目检查说成当前补丁之前的结果。实际 Trace 有四次成功编辑，补丁保留这些修改，最后一批检查是在第 32 轮该补丁上执行。

原因是 task_summary 按文件只保留最新编辑片段，后一次编辑覆盖了此前动作。现在摘要按文件记录成功编辑次数，保留最早和最近三次的片段，标明它们是历史动作，不是完整当前 diff；历史检查另标是否对应当前源码补丁，并明确当前有效性单独记录。恢复快照后排除旧的编辑动作。

定向验证确认四个实际编辑调用进入最终上下文，第 32 轮历史检查与当前已失效检查区分，摘要为 3,799 字符，恢复后旧编辑不再作为当前动作证据。证据：[focused-summary.json](../experiments/2026-10-08-unlimited-tokens/focused-summary.json)、[修正后事实摘要](../experiments/2026-10-08-unlimited-tokens/corrected-summary.json)。没有再次调用真实模型，原始最终答复与失败结果保留不改。临时驱动、工作区和容器已清理，没有新增工程依赖的测试脚本。
