# 子问题执行与项目检查复用

## 目标与依据

上一轮 intword 通过，但跨文件仍没有编辑；两题都没有使用计划工具。跨文件已经复现第一个问题，却继续调查其他需求，九次带工作记录的压缩中六次缺少可容纳的源码快照。intword 同一任务还执行了多次配置检查。接下来先落实当前子问题，再减少重复检查，只复测一个跨文件真实任务。

## 计划初始化

- 普通仓库任务开始时，用一次无工具请求生成结构化计划：每项记录需求、状态、文件、未验证假设和下一动作；第一项执行中，其他项待处理。简单任务只需一项。
- 该请求使用同一模型，最多 1,536 输出 Token，计入原来的步数、用量、超时和 Trace。DeepSeek 使用既有无工具请求的 none 推理配置，不使用思考模式不支持的强制工具选择。[官方接口说明](https://api-docs.deepseek.com/api/create-chat-completion/)
- 初始化只生成计划，不能作为任务完成。后续正常工作提供全部工具，每轮上下文末尾再次展示当前子问题，要求定位后先修改、确认行为，再切换独立需求。
- 计划中的目标文件进入现有源码快照保留优先级；路径与假设仍需现场确认。大范围输出仍可能超出保留容量，这个限制没有因计划初始化自动消失。
- update_plan 与初始化共用字段校验；未完成需求中只允许一项执行中。新任务清除旧计划，续跑保留原计划。
- 如果中断发生在计划响应保存后、计划写入前，恢复时直接解析已经保存的响应，不再调用模型。计划响应不进入完成任务的快捷分支。
- 格式错误明确停止并记录，不能靠修补 JSON、猜测字段或隐藏重试生成另一个计划。

定向验证覆盖计划初始化到正常工具请求、用量计入、未完成计划收尾、日志重建、初始化中断恢复和新任务切换。证据：[focused-planning.json](../experiments/2026-10-08-task-focus/focused-planning.json)。尚未执行新的真实任务，节点 S 仍未整体验收。

## 项目检查复用

- 新增 run_checks，只运行用户配置的项目检查；默认复用本次执行中相同补丁的已通过结果，force=true 明确重新执行。返回内容标明实际执行或缓存复用，Trace 记录 project_check_reused。
- 普通 Shell 和 hook 的 Shell 调用在执行前使检查缓存和当前检查元数据失效；只读工具、计划更新和缓存检查读取保留结果。源码补丁变化仍触发自动检查，失败结果不会被复用。
- 最终验证使用同一缓存，避免模型调用 run_checks 后又重复执行同一套检查。不同运行之间启动了新的容器环境，不继承上一次运行的内存缓存。
- run_checks 遵循写操作权限；没有配置检查时返回明确错误。复现脚本与配置检查分开执行，避免普通 Shell 输出被误当成结构化项目检查记录。
- 事实摘要保留历史自动检查证据，分别记录当前检查与之前执行过的检查，防止缓存失效后声称没有运行过测试。

两个临时 Docker 场景验证了缓存读取、强制执行、Shell 与 hook 失效、最终验证复用和日志重建；另确认只读模式阻止显式检查工具。证据：[focused-check-reuse.json](../experiments/2026-10-08-task-focus/focused-check-reuse.json)。场景数据保留为 JSON，临时工作区已经删除，没有永久测试脚本。

## 有限真实验证

实现并提交上述两部分后，只运行 boltons 跨文件一次，固定原任务、源码树、镜像、模型、80 步和 120,000 Token。通过需满足目标源码补丁、当前配置检查、独立行为验证、状态重建及计划完成。失败即停止扩大验证，单次成功也不代表节点 S 整体验收。
